# Upgrading dw-harness from v1 to v2

[中文版](upgrade-from-v1.md)

This guide is for teams already using the v1 template. v2 keeps the OneData eight-step workflow, the MaxCompute → StarRocks mainline, the four subagents, the 23-item self-test and the nine DQC categories. What changed is how the harness is installed, how the repository is laid out, how commands are named, how hooks behave, and how acceptance is recorded.

## Decide which installation you want

- If your project has `.claude/hooks/validate_sql.py`, `block_dangerous_ddl.py` and `inject_context.py` registered in `settings.json`, it is a standard v1 project.
- If you have customised hooks, skills, agents or settings, back them up first. `dw init` reports conflicts and leaves unrecognised files untouched.
- If you want to keep the copy-template model and avoid the plugin, use the template path. Command names stay as they are.
- If you want Marketplace updates and less per-project maintenance, use the plugin path.

Do not install both. The plugin and the template both register hooks; running them together duplicates checks and blocks. Their hook scripts use different paths, so the migration de-duplication does not merge the two sets.

## What changed

| Area | v1 | v2 |
|---|---|---|
| Distribution | Copy `template/.claude` | Claude Code plugin, `dw` CLI, and copy template |
| Source of truth | Edit `template/.claude` directly | `src/`; `plugins/` and `template/` are generated by `build.py` |
| Commands | `/dw-etl` and seven other bare commands | Plugin mode uses `/dw-harness:dw-etl`; template mode keeps bare names |
| Hooks | Three Python scripts, Bash only | Seven adapters, `Bash\|PowerShell`, fail-closed policy hooks |
| Agents | `agents/<name>/<name>.md` | Flat `agents/<name>.md`, `model: inherit` |
| Skills | Eight | Fifteen: the original eight plus bootstrap, contract, check, next, review, backfill and an on-demand SQL reference |
| Conventions | `.claude/CLAUDE.md` plus `context/` | Root `CLAUDE.md`, `AGENTS.md`, `.claude/rules/` |
| Configuration | Environment variables and filename heuristics | `.claude/dw/harness.json`; the legacy `DW_HARNESS_DIALECT` variable still works |
| Acceptance | Conversation and documents | `dw check` four-state report plus input-bound evidence |
| Python | 3.9+, invoked as `python` | 3.9+; plugin hooks use `python` from PATH, template installs can pass `--python` |

`CLAUDE.local.md` is a Claude Code local-memory feature. dw-harness does not generate it or depend on it. Iteration state belongs in the root `CLAUDE.md`, `.claude/dw/state.json` and the step deliverables.

## Breaking changes

**1. Plugin commands are namespaced.**
`/dw-etl` becomes `/dw-harness:dw-etl`. Template mode is unchanged. Update runbooks and scripts that spell out command names.

**2. Hook files were renamed, and one behaviour changed.**
`validate_sql.py` becomes `validate_post.py`. It still runs after a write, but the file is already on disk; `exit 2` feeds the error back to the model so it can correct the file. It does not prevent the write.

`block_dangerous_ddl.py` becomes `guard_shell.py`. It covers PowerShell as well as Bash, and recognises `-f` scripts, `--file=`, compound commands and `.cmd`/`.exe` clients.

`inject_context.py` becomes `session_context.py` plus `post_compact.py`. SessionStart injects the state card; PostCompact only writes local state and does not inject context.

**3. `init` no longer deletes `.claude`.**
The v1 script removed the directory and copied a fresh template. v2 merges: it reads the existing `settings.json`, adds only missing entries, writes `.bak-<timestamp>`, and tracks managed files in `.claude/dw/managed.json`. Files you modified are reported as conflicts and left in place.

**4. Agents are flat.**
`agents/data-comparator/data-comparator.md` becomes `agents/data-comparator.md`. Flatten custom agents as well, and check that their frontmatter does not rely on `permissionMode`; the plugin environment ignores it, so capability limits should use `tools`.

**5. `FileChanged` was removed.**
The v1 watcher assumed glob matching, but `FileChanged` registers literal filenames. Out-of-band edits are handled by `dw lint --changed` / `dw check --changed` in the CLI or CI instead.

**6. Strict evidence requires a key.**
`dw check` in strict mode does not accept an unsigned producer field. The producing and checking shells need the same `DW_HARNESS_EVIDENCE_KEY`. For local work, use `--mode local` or generate a key with `dw evidence keygen`. In CI, store it as a secret.

**7. Plugin hooks expect `python` on PATH.**
The PreToolUse hooks use `onFailure: "block"`. If the interpreter is missing, Bash and Write/Edit calls are blocked. On macOS or Ubuntu installations that only provide `python3`, activate an environment that provides `python`, or use template mode with `dw init --python python3`.

## Migration A: plugin (recommended)

1. Back up and check the worktree:
   ```bash
   git status
   cp -r .claude .claude.v1.bak
   ```
   PowerShell:
   ```powershell
   Copy-Item -Recurse .claude .claude.v1.bak
   ```

2. Install the plugin:
   ```text
   /plugin marketplace add pugyy/dw-harness
   /plugin install dw-harness@dw-harness
   ```

3. Generate the project-side files:
   ```text
   /dw-harness:dw-bootstrap
   ```
   With the CLI installed, the equivalent is:
   ```bash
   dw init --target . --mode plugin --dry-run
   dw init --target . --mode plugin
   ```
   Plugin mode does not write hook wiring; the plugin supplies it. `--python` does not affect hooks there; it is only used for the `--statusline` command and the `--mcp` server registration. Plugin hooks always use `python` from PATH.

4. Inspect `settings.json`. The migration removes hooks it can identify as v1 (`python .claude/hooks/validate_sql.py` and the other two), while keeping custom permissions, status line and unrelated hooks. Customised v1 hooks are listed as conflicts and need a manual decision.

5. Check the project files:
   - root `CLAUDE.md` references `@AGENTS.md`;
   - `.claude/rules/` contains both v2 rules and your team rules;
   - migration only appends `@AGENTS.md` to root `CLAUDE.md`; it does **not** move the contents of `.claude/CLAUDE.md`. Copy the old iteration state, current table, version and constraints into root `CLAUDE.md` by hand;
   - custom skills and agents are still present, and nested agents are flattened.

6. Run:
   ```bash
   dw doctor --mode plugin
   ```

## Migration B: template (offline or no plugin)

1. Back up `.claude` and confirm `settings.json` parses.
2. Preview:
   ```bash
   dw init --target . --python python --dry-run
   ```
3. Apply:
   ```bash
   dw init --target . --python python
   ```
   Or use the repository wrapper:
   ```bash
   bash init.sh /path/to/project
   ```
4. Review `.bak-*`, `.claude/dw/managed.json` and the conflict list.
5. Run:
   ```bash
   dw doctor --mode template
   ```

`dw init --python` only affects template hook wiring and the optional status line. Plugin mode follows the PATH interpreter rule above.

## Verify after migration

- `SELECT t.*` and `SELECT DISTINCT t.*` hit `no-select-star` in both the hook and `dw lint`. `COUNT(*)` and `'drop table'` inside a string literal do not.
- An `INSERT OVERWRITE` without `PARTITION` fails both `dw lint` and the PostToolUse check.
- `odpscmd -e 'DROP TABLE db.t'` is denied by PreToolUse. Point the hook at a nonexistent interpreter and confirm it still blocks.
- `dw check` returns PASS/FAIL/UNVERIFIED/N/A and exit codes 0/1/2.
- Edit a bound SQL file and rerun `dw check`; the old evidence becomes UNVERIFIED rather than staying PASS.
- Your existing status line is still there. `dw init --statusline` adds the dw status line only when no `statusLine` exists.
- CI uses `dw lint --changed` and `dw check --changed` instead of relying on an interactive Claude Code session.

## What stays the same

- The OneData eight-step sequence and its deliverables.
- The MaxCompute → StarRocks mainline.
- The four subagent roles: exploration, SQL validation, self-test, reconciliation.
- The 23 self-test items and nine DQC categories.
- Path-scoped rules, SQL conventions, `DECIMAL(20,4)` for money, and `partition_dt`.
- Custom skills, rules, permissions and status line entries: migration merges, it does not remove them.

## Onboarding legacy tables

For a historical table without a contract, `dw check` reports `contract-validate` as UNVERIFIED, not FAIL. To put it under contract, copy `contracts/contract.example.json` to `contracts/<table>.json` and fill in the table identity, grain, business key, partition, column types, currency/unit, quality thresholds and SLA. Then run:

```bash
dw contract validate contracts/<table>.json
dw contract compile contracts/<table>.json
```

The next `dw check` uses the new contract. Breaking field changes still require a recorded migration decision.

## Known limits

- `plugin-validate` requires `CLAUDE_CODE_OAUTH_TOKEN` and a manual dispatch; it was not run for the release.
- MaxCompute, StarRocks and DataWorks adapters are code-complete but have not been tested against live instances. Reproduction steps are in `docs/e2e-demo.md`.
- Plugin hooks require `python` on PATH. Environments with only `python3` need an interpreter shim or a template install.
- The package is not on PyPI; install the CLI from the repository.
- v1 had no evidence chain, so there is no `dw-evidence/2` history to migrate.

## Rollback

Migration does not delete v1 files. `settings.json` and `CLAUDE.md` get `.bak-<timestamp>` copies. Back up the current state first:

```bash
git status
git checkout -- .claude CLAUDE.md
```

`git checkout` only restores tracked files. `AGENTS.md`, `.claude/dw/` and new `.claude/rules/` files created by `dw init` are usually untracked and will remain. Preview them before cleaning:

```bash
git clean -nd .claude AGENTS.md
```

After confirming the list contains no team-owned untracked files, remove them:

```bash
git clean -fd .claude AGENTS.md
```

`.claude.v1.bak` is also untracked. Add it to `.git/info/exclude` or `.gitignore` so it does not keep appearing in `git status`.

If the plugin is installed, uninstall it:

```text
/plugin uninstall dw-harness@dw-harness
```

If `dw init` wrote `managed.json`, inspect its managed-file list before deleting `.claude`, so you do not remove team content by accident.
